# Security rules and audit

Moved from CLAUDE.md when it was cut to its essentials (D90): the same rules and reference, unchanged, read when a task touches this area. A rule here binds exactly as one in CLAUDE.md, which stays the source of truth (if a task conflicts with either, stop and ask).

## Security rules

- Invite-only accounts tied to a lot or board role. No open signup.
- Strong authentication is mandatory for every account, owners included: a passkey, or a password or emailed sign-in code followed by TOTP or a passkey. Never password-only. Email codes never count as a second factor.
- Lost authenticators (D58): the two-board-member assisted reset plus a single-use enrollment code handed over out of band works for everyone and is the only path for staff roles (anyone with, or within 30 days of, a board seat, an office or a manager, sysadmin, auditor or ARC reviewer role). Ordinary logins (owners, account contacts, tenants, former owners) may instead use self-service recovery (`accounts/recovery.py`): an emailed single-use link starts a request that waits `recovery.wait_hours` (board setting, default 48, never under 48), alerts every email on file, the opted-in text number and the board at once, and is cancelled by the person (signed-in page, or simply signing in with their passkey or app) or any board member; after the wait it is finished only in the browser session that opened a fresh link (old authenticators removed, enrollment window opened). For `recovery.lock_hours` afterwards (default 48, never under 24) services refuse votes, ballots, survey answers, proxies, contact/notice/text/mailing changes, statement-email and digest changes (D87), autopay changes and account change requests via `accounts.recovery.refuse_if_locked`. The neutral form never reveals which path applies. A login that never had a passkey or app (missed its setup window) may instead get a new setup link from the board, to the Person's email (D59, `accounts.services.setup_again_refusal`, which refuses after any enrollment, reset or account recovery); the pages open without an authenticator are fixed by `accounts/tests/test_enrollment_review.py`.
- Can't sign in? (D62, `accounts/signin_help.py`): the sign-in page has one help link, "Can't sign in?", to a guided page (`signin_help`) that asks what's wrong and routes to the existing flows (password reset; recovery code or other device, else account recovery; setup link expired → "Ask the board"; no email → board-assisted only; locked out → the configured wait). Its pages are sign-in steps that never show whether an account exists or any portal data (PUBLIC in `core/tests/test_url_matrix.py`). "Ask the board" answers every address the same way and queues only a login id; the worker records `auth.setup_link_requested` (ids only) and the board's My items entry only for a login that may get a new setup link (`accounts/setup_requests.py`); no email is sent. Old direct URLs (password reset, recovery form, emailed links) keep working.
- Forgot password (D58): allauth's emailed reset link, then the passkey, app or a recovery code, then a new password; it never signs anyone in; "Your password was changed" goes to every email on file.
- A login with no authenticator may enroll one only in the browser session that accepted its invitation, redeemed a reset code or finished a self-service recovery, within `MFA_ENROLLMENT_WINDOW_SECONDS`; otherwise it is signed out. Re-authentication accepts a password or an authenticator, never an emailed code. Recovery codes are shown once (that session may print or download them); My items asks for a backup sign-in method until there are two strong ones, and for new codes when two or fewer are left.
- Official notices step (D44): only after MFA is set up ("I've saved them"), current owners on the deed who never answered see `notice_choice` once (email or post, nothing pre-selected; wording and `CONSENT_VERSION` in `community/notices.py`, recorded by `community.services.record_notice_choice`); skipping or older logins get a My items to-do, never a blocking page. Paper and letters read `community.services.postal_address` (structured address, then old text, then the home's address). Text alerts stay opt-in with a texted code; adding a phone never opts in.
- Invitations go only to the email on the Person record and are created only by the board.
- Passwords: 12+ characters, no composition rules, common-password and breached-password (HIBP k-anonymity, fail-open) checks.
- Secure cookies, CSRF, HSTS, CSP, strict `ALLOWED_HOSTS`, `DEBUG=False` outside local dev.
- File uploads: type allowlist (by content, with Office macro/embedded-object/remote-template checks), size limits enforced before buffering, malware scan hook (rescans are new append-only records), stored in a private bucket under random keys, streamed only through the app after an authorization check (never signed URLs), with names that always end in the validated extension. Published document versions are immutable.
- No secrets, tokens, or real personal data in the repository, fixtures, logs, or error reports. Local and POC data is synthetic only.
- Log structured events without personal data. Do not log request bodies, exception messages, or URLs carrying tokens (gunicorn access logs are off).
- Proxy headers (client IP, scheme) are trusted only from `TRUSTED_PROXY_CIDRS`.
- The application never handles card or bank account numbers. (Later: Stripe hosted Checkout only.)
- Treat all user input and uploaded files as hostile.
- No anonymous access: every page needs sign-in except the sign-in steps themselves (login, invitation, reset code) and, by the owner's approved exception (D79), the vendor onboarding form (`vendor_onboarding_start`/`_form`/`_upload`/`_submit`/`_done`, built as tightly as the sign-in steps: one emailed 256-bit link per round stored as a keyed hash, swapped for a 2-hour session bound to that round and redirected off the URL, ended by submission, expiry or a new link, rate-limited per client and link, neutral answers, strict CSP with no script, no referrer, no portal navigation or data beyond the association's name; that session reaches nothing else, `operations/tests/test_vendor_onboarding_public.py`). Emailed links lead to signed-in pages; links that record a vote are personal and single-use, and casting needs recent re-authentication (D24).

## Audit

`audit.AuditEvent` records who did what to which object, when, and from where, for logins, MFA changes, role changes, document views and downloads, ARC actions, exports, and sysadmin access. Append-only. Provide a board-visible view of sysadmin activity.

- IP addresses live in a separate table purged after `AUDIT_IP_RETENTION_DAYS` (the purge is itself audited); the core event is permanent.
- Failed logins for unknown emails store a keyed hash (`AUDIT_HASH_KEY`), never the address. No user-agent strings. Event metadata is checked against a per-action field allowlist.
