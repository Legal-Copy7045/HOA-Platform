# Deployment and the POC VM

Moved from CLAUDE.md when it was cut to its essentials (D90): the same rules and reference, unchanged, read when a task touches this area. A rule here binds exactly as one in CLAUDE.md, which stays the source of truth (if a task conflicts with either, stop and ask).

- Updates without a terminal: System status → Check now / Install now / Install tonight (sysadmin); the VM's `infra/poc/portal-agent.sh` timer does the work (D25) and offers only the newest release tag on main (D90; `infra/poc/update-portal.sh --ref <branch>` deploys a branch on purpose). Install tonight (D38) sets `UpdateStatus.state='scheduled'` and `scheduled_for` (next `UPDATE_NIGHTLY_HOUR`, default 4, site time); the agent turns it into a request when due. New `UpdateStatus` columns must be nullable or carry a `db_default`, because an update pulls the agent before migrating
- Compose files always together (D91): on the VM the portal is `docker-compose.yml` plus `docker-compose.tunnel.yml`, and `.env` holds `COMPOSE_FILE=docker-compose.yml:docker-compose.tunnel.yml` (`make-env.sh`; `start-portal.sh` and `update-portal.sh` add it to an older `.env` with `lib.sh` `ensure_compose_file`, appending one line), so plain `docker compose ...` in the checkout uses both. cloudflared stays on the `edge` network only (security review E3/E9: never Postgres or the file store): `start-portal.sh` and `update-portal.sh` (even with nothing to install) disconnect it from any other network (`cloudflared_edge_only`, idempotent); the agent reports its networks each minute and the "Tunnel network" health check fails while it is on another. Never `docker network connect` it to the default network
- Restart (D91): System status → Restart the portal (`system_restart`: sysadmins, then a fresh password or passkey check, then a confirmation page) requests the `restart_app` server task, at most once every 10 minutes (`host_tasks.RESTART_COOLDOWN`), one task at a time, audited like every task; the agent runs `infra/poc/restart-portal.sh` (`docker compose restart web worker` with both files, web recreated only if it lost `edge`, waits for healthy, then `cloudflared_edge_only`)
- Server tasks (D36, Admin → Server tasks, `server_tasks`): sysadmins start `backup`, `restore_drill`, `restore_drill_offsite`, `offsite_lock_check`, `harden_host`, `health_check`, `reseed_demo` (demo portals only, with a dataset, D53), `restart_app` (from its own page, D91) (`core/host_tasks.py`, `system.run_task`; board sees history with `system.view_tasks`); the web app only inserts a `core.HostTask` row, the VM agent maps the kind in `infra/poc/host-tasks.sh`'s `case` to a fixed command and writes back through psql variables; `manage.py record_host_tasks` audits results. A new reusable host operation is added there, not as a script people run
- File storage on the POC: local SeaweedFS (`COMPOSE_PROFILES=local-store`) or Cloudflare R2; switch with `sudo bash infra/poc/move-files-to-r2.sh`
- Production settings by stage (D57, `core/settings/production.py`): `DEPLOYMENT_STAGE` is `production` (default) or `poc`; both need `DOCUMENT_SCANNER=clamd`, `DOCUMENT_CLAMD_ADDRESS` and `DOCUMENT_REQUIRE_CLEAN_SCAN=true` (also set in `docker-compose.tunnel.yml`); production also needs `EMAIL_REDIRECT_ALL_TO` empty and HSTS of at least a year (the default there)
- Malware scan queue (D57, `documents/scan_queue.py`): a scan that got no answer stores why (`detail`/`scan_detail`); `documents.tasks.scan_file` retries after commit, `scan_sweep` every 10 minutes while ClamAV answers; System status lists waiting files in operations terms only (never names, titles or owners) with "Scan waiting files now" (`system.run_task`, audited counts); health check `scan_queue` fails after 30 minutes
- Images (D57): infrastructure images in the compose files are `tag@sha256:digest`, updated only by Dependabot `docker-compose` pull requests that CI tests; never `latest`, no pulls on the VM outside the portal update; a pin needs its Dependabot entry (`core/tests/test_image_pins.py`)
- POC VM: see `infra/poc/README.md` and `docs/runbook.md`; update in one step with `sudo bash infra/poc/update-portal.sh`; test outgoing mail with `sudo bash infra/poc/test-email.sh [address]`

## Deployment targets

- Third-party service keys are entered in the browser on System status → Keys and connections (D93, `docs/claude/security.md`); the set-*.sh scripts below are an optional fallback (a value saved in the portal wins over `.env`). `CREDENTIALS_KEK` and BANK_FEED_TOKEN_KEY are created by `start-portal.sh` on the first start after an update (`lib.sh` `env_ensure_secret`), so installing the update is the only server step.
- Reusable host operations are started in the portal (Admin → Server tasks) and run by the VM agent from a fixed allowlist (D36). OS-level scripts are only for one-time setup (`provision-vm.sh`, the first `harden-host.sh` run) and steps that take secrets typed by a person (`setup-offsite-backups.sh`, `set-stripe-key.sh`, `set-teller.sh`, `set-usps.sh`, `set-bounce-mailbox.sh`, `set-smtp2go.sh`, `set-vendor-key.sh` (makes its key on the server, nothing typed, D79), `move-files-to-r2.sh`): these scripts never pass a secret through the web app; the service keys among them are now optional, as Keys and connections takes them in the browser (D93). They edit `.env` only through `infra/poc/lib.sh`'s `env_backup` / `env_update` / `env_restore_keys` / `env_discard_backup` (only their own keys, every other line kept, mode 600, a failed check puts back only their keys, the `.env.before-*` copy shredded afterwards; no script writes a key another one owns, `core/tests/test_env_helper.py`). Secrets reach only the containers that use them: the bounce mailbox and USPS passwords the worker, the SMTP2Go key web and worker (web sends mail while a person waits), never migrate or create-bucket; the others get a `*_SET` flag. Keys saved on Keys and connections are read from the database by web and worker alike (both hold `CREDENTIALS_KEK`), so that container split (EXP-003) applies only to values still in `.env`.
- POC: a Proxmox VM on an isolated VLAN, exposed only through a Cloudflare Tunnel (cloudflared in compose, web publishes no port), with a dev subdomain behind Cloudflare Access. No LAN access mode.
- Production: managed host or hardened VPS, behind Cloudflare, with the HOA owning all accounts.
- A full restore-and-migrate drill to a scratch environment must be done before any real data or live payments.
