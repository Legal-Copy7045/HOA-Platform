# Decision record

Decisions agreed during Milestone 1 planning, with the reasoning. CLAUDE.md
states the resulting rules; this file explains why. Add new entries rather
than rewriting old ones; mark superseded entries as such.

## D1. Board seats and offices are separate records (Q1)

A board seat (membership, declarant-appointed or owner-elected, with a term) is
different from an office (president, VP, treasurer, secretary). Modelling only
offices could not represent directors-at-large, and the declarant flag belongs
to the seat. PA UPCA (68 Pa.C.S. § 5303) governs the declarant-control
transition; thresholds come from the Declaration/bylaws and will be
configuration with citations. M1 records seat type only; it enforces nothing.

- Officers must hold an active seat (setting, can be relaxed with a bylaws citation).
- A seat ends only when `ended_on` is recorded; directors typically serve until
  a successor is elected. The board page warns on terms past `term_end`.
- ARC appointments are dated `RoleAssignment`s with `appointed_by` (board or
  declarant) and an optional citation.

## D2. Email (Q2)

- Local: Mailpit. Tests: in-memory backend. Production: Hostinger SMTP via env.
- POC: `EMAIL_REDIRECT_ALL_TO` (set only in the VM's `.env`) sends every message
  to one inbox; the app logs a warning while it is set. Seed data uses
  `@example.com` (reserved, never delivers).
- Invitation emails contain only the link and the community name.

## D3. Breached-password check (Q3)

HIBP range API with k-anonymity (5-character SHA-1 prefix leaves the server).
Fail-open with a warning log on API failure; 3-second timeout; disable with
`PASSWORD_BREACH_CHECK=false`; mocked in tests. Written in-house (~30 lines)
instead of adding a dependency.

## D4. Authority and two-person rules (Q4)

- The board has five members and no internal rules yet, so every board member
  can perform every board action. Permissions live in one map so offices can
  be given distinct powers later.
- Every action must remain performable by at least two people with MFA; the app
  warns (does not block) when that fails, so a resignation can still be recorded.
- Granting sysadmin: nominator plus a different approving board member, 7-day
  expiry, whole board emailed. Revoking: any one board member, immediately.
- No self-grants. Invitations grant nothing.
- Bootstrap (4c-i): `bootstrap_first_officer` may create one initial sysadmin
  without approval; audited, shown to the board, refused once one exists.

## D5. Strong authentication for every account (Q5, Q10)

Supersedes CLAUDE.md's original "optional for owners".

- Accepted sign-in: passkey; or password then TOTP/passkey; or emailed code
  (6 digits, 10 minutes, 3 tries, tied to the requesting browser) then
  TOTP/passkey. Never password-only. Email is never a second factor, because
  email already controls password reset.
- Code rather than magic link: corporate link scanners consume single-use
  links, and a code is bound to the browser that asked for it.
- Password minimum 12 (NIST SP 800-63B rev 4 allows shorter when MFA is always
  required; 12 is a moderate ask).
- Lost everything: board member A starts an assisted reset and records how
  identity was confirmed; a different board member B approves; all
  authenticators and sessions are removed; a single-use enrollment code (24h)
  is handed over out of band. This closes the gap in which someone with the
  password could enroll their own device.
- Cost accepted: more board support. Mitigations: a help page, spare hardware
  security keys, printable recovery codes.

## D6. Proxy trust and network exposure (Q6)

- Client IP and scheme headers (`CF-Connecting-IP`, `X-Forwarded-Proto`) are
  trusted only from `TRUSTED_PROXY_CIDRS`; otherwise ignored. Prevents lockout
  evasion and audit-log poisoning by spoofed headers.
- cloudflared runs as a compose service on the POC; the web container publishes
  no port there. Cloudflare Access gates the dev hostname.
- No LAN mode. Testing from other devices goes through the tunnel.
- Lockout: 5 failures per email+IP (30 min); 20 per email per hour (15 min).
  Passkey sign-in is not blocked by password lockout.

## D7. Personal data in audit (Q7)

- Unknown-email failed logins: keyed HMAC of the normalised address only.
- IPs in a separate table, purged after 365 days (configurable); core events permanent.
- No user-agent strings. Metadata field allowlist per action, enforced in tests.
- Open: confirm retention with the association's counsel.

## D8. Two database roles in M1 (Q8)

A trigger alone does not bind the role that owns the table (it can drop the
trigger or TRUNCATE). Migrations run as an owner role; web and worker run as an
app role with DML only, no TRUNCATE or DDL, and no UPDATE/DELETE on append-only
tables. Grants are re-applied after every migrate (`core/db_roles.py`). The
owner credentials never reach web or worker containers. Residual risk: anyone
holding owner or superuser credentials can still alter data.

## D9. Sysadmin scope (Q9)

No Django admin in production (it bypasses scoping, two-person rules and audit).
Sysadmins get invitation and system-status pages only. Data fixes use
break-glass management commands that require `--actor` and `--reason` and go
through the service layer. Every sysadmin portal request is audited. Direct
database access is restricted by runbook policy, not software.

## D10. SeaweedFS replaces MinIO locally

MinIO stopped publishing pre-built images in 2025, so the local S3-compatible
store is SeaweedFS (actively maintained, single container). Production remains
Cloudflare R2. The app sees only standard S3 settings.

Open for Milestone 2: signed URLs point at `S3_ENDPOINT_URL`, which browsers
cannot reach locally. Either add a separate public endpoint setting or stream
downloads through Django after the authorization check.

## D11. Custom user model before any user reference

The email-based `accounts.User` landed with the audit app (step 2) rather than
step 4, because `AuditEvent.actor` references users and Django cannot switch
user models after such a migration exists. Users are never deleted
(`on_delete=PROTECT` from audit events; `delete()` raises).

## D12. Dedicated Cloudflare tunnel for the POC

Reusing the existing home tunnel would need a firewall hole from the home
network into the isolated VLAN, would widen the set of hosts trusted to set
client-IP headers, and could not be handed to the HOA later. The dedicated
`hoa-portal-poc` tunnel's connector runs inside the VM.

## D13. cloudflared follows the latest release

*Superseded by D57 (2026-11-26): cloudflared is pinned to a release and digest and updated by Dependabot pull requests; the daily timer is removed.*

cloudflared cannot update itself inside a container, and Cloudflare stops
supporting old releases. The tunnel overlay uses `cloudflare/cloudflared:latest`;
a systemd timer on the VM pulls daily and restarts only that container when
the image changed. Trade-off accepted: the edge connector updates without
review, as it is Cloudflare's own component already trusted with all traffic.
The portal image itself is still built from reviewed code.

## D14. Authorization mechanics (step 4)

- Roles are computed from dated records on every check, never cached on the
  login, so revocation applies on the next request.
- `RoleAssignment` lives in `community` with Person, seats and offices.
- The default manager of every scoped model raises on any unscoped query,
  including reverse relations (`lot.ownerships`). We chose loud failure over a
  silently filtered default so a forgotten scope shows up in tests. Django's
  own validation and forward foreign keys still work.
- Owners see current co-owners of their lots but not past owners. Sysadmin and
  ARC roles grant no owner data by themselves (D9).
- Services enforce permissions themselves rather than trusting views; an
  explicit `SYSTEM` actor covers bootstrap and seed data, and a missing actor
  is an error.
- Board members may end their own seat (resignation) without the manage
  permission; they cannot grant themselves anything.

## D15. Sign-in mechanics (step 5)

- allauth's MFA step applies after a password *or* an emailed code; only a
  passkey sign-in skips it (a passkey is itself multi-factor). "Trust this
  browser" is off.
- `RequireMFAMiddleware`: a signed-in account without TOTP or a passkey can
  reach only the enrollment pages and sign-out. Recovery codes alone do not
  count. Applies to every account, checked on every request.
- Lockout: django-axes, 5 failures per email+IP, 30 minutes, kept in the
  shared database cache (no per-attempt rows holding emails or user agents).
  The per-email ceiling (20 per hour, any IP) is allauth's rate limit; its
  block lasts until the hour window passes rather than exactly 15 minutes.
- Self-service email change and signup URLs return 404.
- Residual gap, accepted: a new account is password-only between accepting the
  invitation and enrolling (same session, enrollment forced immediately).
- Recovery codes are shown by allauth after enrollment; we do not force a
  "I saved them" confirmation in M1.
- Authenticator-app codes from the neighboring 30-second window are accepted
  (`MFA_TOTP_TOLERANCE = 1`, RFC 6238 s.5.2). allauth's default of 0 rejected
  codes typed as the window rolled over (found on the POC).

## D16. Milestone 2 build (2026-11-25, directed overnight)

- Scope and user decisions: `docs/milestone-2-plan.md`.
- One workflow engine (`core.workflow`) for ARC, violations, records
  requests, work orders, invoices, collections and resale certificates;
  every step is an append-only WorkflowEvent plus an audit event.
- Files attached to workflow objects are append-only `documents.Attachment`
  rows using the same validation and scanning as the library, served only
  after the owning object's scoped lookup. Downloads stream through Django;
  no signed storage URLs reach the browser.
- PDFs (decision letters, notices, statements, resale certificates) come
  from a ~90-line text PDF writer (`core.pdf`) rather than a dependency.
- Ledger: one account per lot, append-only scoped entries in cents;
  prepayment is a credit balance drawn down by monthly charges; aging
  applies credits oldest-first; corrections are reversals. New owners see a
  brought-forward balance, not the previous owner's history.
- Late fees cannot be posted (LEDGER_LATE_FEES_ENABLED=false) pending the
  PA law review. Collections are tracking only.
- Formal votes freeze quorum/pass rules and their citations when opened
  and are labelled not for binding use until counsel review. Ballots are
  append-only; secret ballots hide voter choices in the UI (the database
  still links ballot to lot to enforce one vote per lot).
- Invoices: threshold rule invoice.dual_approval_cents ($500), two
  distinct board approvers at or above it, the entrant never approves.
- Resale certificate content is a draft for counsel to check against
  68 Pa.C.S. § 5407.
- Manager role added (data entry and workflow steps only).

## D17. Security review changes (2026-11)

Full findings and fixes: `docs/security-review-2026-11.md`. Decisions that
change earlier ones:

- **Invitations (changes D4/D9):** only the board creates invitations, and
  only to the email on the person's record. Sysadmins may re-send or revoke.
  A printed invitation link exists only to finish the first-officer bootstrap.
- **Enrollment window (refines D5/D15):** a login with no authenticator can
  enroll one only in the session that accepted the invitation or redeemed a
  reset code, within `MFA_ENROLLMENT_WINDOW_SECONDS` (1 hour). This closes the
  "accepted residual gap" in D15. Re-authentication never accepts an emailed
  code.
- **Owner visibility of lot history:** owners see ARC requests, violations
  and resale records from their own ownership period (plus unresolved
  notices); violations only after notice. The board sees everything.
- **Frozen decisions:** vote rules once open, invoice amount/vendor/number
  once submitted, and the approvals an invoice needs are fixed (database
  triggers). Issued resale certificates are stored, not regenerated.
- **Deployment:** production needs `TRUSTED_PROXY_CIDRS` (or
  `NO_TRUSTED_PROXY=true`); demo data only with `DEPLOYMENT_STAGE=poc`;
  web/worker refuse to run as the database owner; cloudflared has its own
  network with only web.
- **Open for the board:** a second board member to approve new seats (A3);
  whether formal secret ballots must be anonymous in the database (D12).

## D18. Accounts, account contacts and former owners (2026-11-25)

The owner asked for accounts that hold several people, belong to a lot, and go dormant on sale, and for sellers to keep a read-only login for their history. An account is one ownership period of a lot (re-recording owners, such as adding a spouse, keeps the account; a sale opens a new one). Contacts not on the deed get access from their kind (authorized, view-only, tenant), never from self-service. Former owners see only their own era: statements cut at the sale date, and their own ARC requests, notices and resale requests. This relaxes the M1 rule "ending an ownership removes access" to "removes access to everything except one's own history", which the owner approved.

## D19. PA law guidance and statutory fallbacks for settings (2026-11-25)

The owner asked for each settings section to show an example from Pennsylvania law. `community/pa_law.py` records, per setting, where the value usually comes from (Declaration, Bylaws, Rules and Regulations, board resolution), a summary of the Uniform Planned Community Act (68 Pa.C.S. Chapter 54) and a worked example. Only where the Act itself supplies a value when the documents are silent is it used as a fallback until the board records its own: meeting notice 10 days (§ 5308), quorum 20% unless the Bylaws differ (§ 5309), resale certificate within 10 days (§ 5407). Everything else stays unset until the board records it. The summaries are orientation, not legal advice, and the page says so; counsel should confirm them before real use.

## D20. Board members are homeowners first (2026-11-25)

The owner pointed out that every board member also owns a home and must use the portal as a homeowner, with board rights added on top, and keep homeowner access after leaving the board. Roles were already additive (Ownership gives the homeowner side, BoardSeat the board side); what was missing was (a) a way to load the real register so board members' own ownerships exist, now `import_register` (check, then `--commit`; matches existing people by email, so the bootstrapped first officer gets their lot), and (b) a menu that keeps the two sides apart: a Homeowner section whose lists show only your own home (`?mine=1`) and a Board section with the review lists. A board member still cannot record their own ownership in the portal (no self-grants); the import runs on the server and is audited. The Homeowner view stays read-only, for seeing another owner's view.

## D22. Neighbor acknowledgements come before board review (2026-11-25)

The owner asked that neighbors acknowledge an ARC request before the board reviews it, with the wording "acknowledgement" rather than "sign-off". The lot's recorded neighbors are on every request from creation and only the board can remove them; the homeowner can add other homeowners (picked by street address and the owners' names on the deed, never tenants or email addresses) or outside addresses. "Request Neighbor Acknowledgements" moves the draft to a new `neighbors` state and emails review links (portal owners a link to the review page, others a single-use link). Neighbors respond "no objection" or "object", and an online objection needs a comment. When nothing is waiting, the request moves to submitted automatically (system actor, audited) and the applicant is emailed. A neighbor who never responds is handled by the board removing them, or by the paper form. Acknowledgements still never decide a request. The kind of project is always a list: a starter list is added by migration when the board has none. Planned start is required on the owner form.

## D23. Secret ballot storage: what "unlinkable" does and does not cover (2026-11-25)

The regression review (SEC-004, BUG-005) found that Postgres itself can link a secret ballot's choice rows to its "this lot voted" row: rows written in the same transaction share a transaction id (`xmin`), and rows written one after another sit next to each other on disk and in the write-ahead log. The application never reads these, the runtime database role cannot change them, and the portal shows no way to join them, so no owner, board member, manager or sysadmin can see how a lot voted through the portal. Someone with direct database or backup access and Postgres knowledge could. D21's "stored unlinkable" therefore means "unlinkable through the application and its data model", not "unlinkable to a database administrator". Closing the gap fully needs a mixing step (choices held and written in shuffled batches by a separate process) or ballots counted by a third party; both are larger designs that need the owner's and counsel's view on whether the residual risk matters for a 44-lot community with board-held backups. Until then: database and backup access stays with the sysadmin and the two-person rules, and this limitation is disclosed to the board. (Closed by D56, 2026-11-26: choices go through a mixing pool and are written in shuffled batches in a separate transaction.)

Also from the same review: outside the POC, a board seat always needs a second board member's approval regardless of the `BOARD_SEAT_SECOND_APPROVAL` environment variable; elections fix the ballot once voting opens (database trigger); a proxy counts only while its grantor still owns the lot; neighbors see an ARC request only after "Request Neighbor Acknowledgements" and only while it is open.

## D24. No anonymous access; personal vote links (2026-11-25)

The owner ruled that nothing in the portal is reachable without signing in: "anything that is emailed out, that drives the recipient to the portal (ARC review, voting, etc) must be authenticated - they don't have to reauthenticate if they have a valid session open, but there can't be anonymous access to any part of the portal." The neighbor acknowledgement single-use links (Milestone 3 phase 7) therefore no longer show anything to an anonymous visitor: neighbors with a login get a link to their signed-in review page; neighbors without one, and addresses outside the community, use the printed form. Links emailed earlier ask for sign-in and then send only the neighboring lot's owner on to their page. The only pages open without sign-in are the sign-in steps themselves (login, accepting an invitation, redeeming a reset code), the health probe and the login background image.

For votes: "if we're logging people's votes, I want to be able to ensure it's them actually voting. Those kinds of votes need to be single use, unique links, but also authenticated as well. I don't want to be able to forward a vote to someone else." Vote and election emails carry a personal link for that person and that ballot (only its hash is stored); it needs sign-in, opens only for the person it was issued to, and stops working once used or when voting closes. Casting a formal vote or an election ballot needs re-authentication within the last few minutes (password or passkey, never an emailed code).

## D25. Updates from System status, and a lighter, faster deploy (2026-11-25)

The owner asked for "update available" on System status and a button to install it without terminal access. The web app gets no access to the VM: a request row in the database (`core.UpdateStatus`, set only by a sysadmin with MFA, audited) is the whole interface. A host-side agent (`infra/poc/portal-agent.sh`, systemd timer every minute, installed by `start-portal.sh`) checks GitHub every 15 minutes or on "Check now", records how many commits the tracked branch is behind, and on "Install update" runs `update-portal.sh` and records the result. Values it writes back (commit subjects) go through psql variables, never shell-built SQL. Only the tracked branch is ever installed (on the POC that should be `main`, which only receives CI-green merges), so the button takes no input.

From the optimization review, accepted without a decision because they change no rule: roles remembered per request (cleared whenever anything that grants a role changes); the two-person coverage check in four queries; gunicorn 2 processes x 4 threads with preload; bytecode compiled into the image; finished background jobs removed after two weeks and worker polling once a minute; container logs rotated; memory caps on web, worker and the file store; Postgres sized for a small VM; updates no longer stop every container (Postgres, the file store, the scanner and the tunnel keep running), base images refreshed weekly instead of every update, documentation-only changes skip the restart, migrations skipped when none are pending; CI runs once per PR commit with cached dependencies and a non-durable throwaway database. Left for the owner: ClamAV memory (on-demand or off-box scanning conflicts with D21's "scanning on"), building images in CI and pulling them on the VM, and R2 instead of SeaweedFS on the POC.

## D26. Malware scanner reloads signatures in place (2026-11-25)

ClamAV holds its signature database in memory (~1.2 GB) and, by default, loads a fresh copy alongside the old one at each signature update (~2.4 GB for about a minute), close to the 4 GB the POC VM has. The owner chose "reload in place": `ConcurrentDatabaseReload no` (`docker/clamav/clamd.conf`, the image's own defaults plus this one line, checked with `clamconf`). Peak memory stays near one copy; scanning pauses for about a minute during each reload, and files uploaded in that window wait as "not yet scanned" until it is back (DOCUMENT_REQUIRE_CLEAN_SCAN keeps them from being downloaded meanwhile). Scanning stays on (D21).

## D31. Off-site backups in a locked R2 bucket (2026-11-26)

The owner chose Cloudflare R2 for immutable off-site backups. The nightly backups are already encrypted and carry a keyed checksum before they leave the VM. They go to a separate R2 bucket (not the files bucket) whose bucket lock rule makes everything under `backups/` undeletable and unoverwritable for 90 days, even with valid keys, so a compromised VM or a stolen token cannot destroy them. A lifecycle rule removes backups after 365 days, which keeps cost low and keeps cleared contact details (D28) from living on much longer in backups than in the portal. R2 tokens cannot be write-only, so the lock is what makes the VM's read-and-write token safe. `infra/poc/setup-offsite-backups.sh` proves the lock by trying to delete a probe file (`check_offsite_lock`, audited). The health check alerts when no local or off-site backup has arrived for 36 hours, and `restore-drill.sh --from-offsite` proves the off-site copy restores. The backup key stays offline and outside the Cloudflare account.

## D32-packets. Meeting packets: who builds them, what owners see (2026-11-26)

The board and the manager may build packets (`meeting.packet_build`), following the existing policy for meeting preparation (`meeting.manage` and `document.manage` both include the manager); building approves nothing. The board packet is filed in a board-only folder ("Meeting packets (board)", visible to board, manager and auditor like other board documents). The owner packet is filed in the owner-visible "Meeting packets" folder, so building it publishes it at once (the button says so); executive sessions get a board packet only. Owner packets leave out receivables aging entirely (even totals), and every collection, violation or delinquency figure. "Approved minutes" means the minutes the board attached to the previous held meeting of the same kind, when owners may see that document; the board packet's draft minutes are chosen from the Minutes documents. Attachments are library documents chosen when building (owner-wide only for the owner packet); minutes and attachments are listed in the index and bundled in the .zip, never copied into the PDF. The reserve figure is the board's own entry on the community profile (the one used on resale certificates), and operating cash is the cash book balance. Owners get the latest build only; the board keeps every version.

## D32-surveys. Surveys: informal, frozen once open, anonymous like secret ballots (2026-11-26)

Surveys sit on the Voting hub next to polls and votes and are never binding. The board drafts them; opening fixes the questions and the survey's details (service, and database triggers as the backstop). Only "share the totals with owners after it closes" can still change, because it is a display choice; written answers are never shown to owners. One response per person (owners, or on a "residents" survey also authorized and view-only account contacts and tenants; former owners never). On an anonymous survey the answers sit under a response row with no person, no time and a random id, and a separate "has responded" row names the person with the day only; the D23 limitation (database-level linkage through transaction ids and row order) applies here as it does to secret ballots. Who has responded is recorded on every survey (as with secret ballots); the pages show only the count. Owner decision welcome on whether view-only contacts should be asked on residents surveys (they are today, since answering is an opinion, not an action on the account).

## D32-search. Portal search shows only what each person can already open (2026-11-26)

One search box covers the portal. Search decides nothing about access itself: each area's provider (`<app>/search.py`) checks the same permission as that area's list page and builds its rows from the same scoped query, so owner-era limits, ARC recusal, internal thread notes, tenant and view-only limits and switched-off features carry over unchanged. ## D32-payments. Open-item accounting and Stripe online payments (2026-11-26)

Owner decisions of 2026-11-26, superseding the fee part of D21:

1. **Online payments by Stripe**, built and tested in Stripe test mode now; live keys come later from the HOA's own Stripe account. Only the server's `.env` holds a key (entered at a hidden prompt, `infra/poc/set-stripe-key.sh`); tests use a fake; no key is ever in the repository.
2. **A surcharge on credit cards only.** Bank (ACH) and debit or prepaid card payments carry no fee; the HOA absorbs their cost (card-network rules forbid surcharging debit and prepaid cards and cap credit surcharges at 3%). The rule `payments.credit_card_surcharge_bp` (default 300, hard cap 300 in code and in the rule) replaces `payments.card_fee_bp` and `payments.bank_fee_cents`, whose recorded values stay in the rule history and are no longer used.
3. **The portal is the HOA's accounting system for owner accounts**: every charge (dues, late fees, other charges, resale fees) has its own number ("Invoice 2026-0142"; dues read "Dues – March 2026") and open balance, and payments are applied to specific charges.

How it was built (choices the board should know):

- **Applications are append-only** (`ledger.PaymentApplication`, model + trigger + runtime role); undoing one is a negative application. The order is the governing rule `ledger.assessments_before_fees` (off = oldest charge first; on = dues first). A payer may direct a payment to chosen charges; the rest follows the rule; leftover money stays as credit and is applied as the next charge posts, so prepaid owners' future months show unpaid and the credit draws down monthly (D30 unchanged). A reversal undoes the applications of what it reverses. Balances are unchanged: open charges minus unapplied credit equals the old balance for every lot (tested on the seeded community). Migration `ledger 0009` rebuilt applications for existing entries by replaying history in posting order.
- **Pull, never push**: no Stripe webhook (D24 forbids anonymous endpoints). The return to the success page is only a hint; the server always asks api.stripe.com. Every checkout is bound to a `PendingCheckout` created before the redirect (random 32-byte nonce, lot, account, person, charges, amounts, test/live mode, 24-hour expiry). A payment is recorded only when the fetched session, PaymentIntent and charge all match (ids, metadata, amount, currency, livemode, succeeded and captured); otherwise nothing is recorded, `payments.mismatch` is audited and the board gets a My item. Recording is idempotent (unique PaymentIntent id; the checkout is consumed under a row lock). Online payments are created only by the Stripe sync: `method="online"` is refused on every manual path.
- **Mode safety**: test keys are refused when `DEPLOYMENT_STAGE=production` (else test cards could "pay" real accounts); live keys are refused unless `DEPLOYMENT_STAGE=production` and `PAYMENTS_LIVE_ALLOWED=true`; every fetched object's `livemode` is checked.
- **Least-privilege restricted key** (runbook): Checkout Sessions write; PaymentIntents, Charges, Balance transactions, Payouts, Disputes and Refunds read only. The portal therefore cannot refund. If a non-credit card paid a surcharge (Checkout's funding filter, `payment_method_options[card][restrictions][funding_types_blocked]` in API version 2026-08-26.dahlia, normally prevents it), the board gets "Refund $X surcharge to lot N (debit card)" and the poller closes it when the refund appears. A credit card on a no-fee session is absorbed and only counted. Link is hidden on card sessions; Apple Pay and Google Pay cannot be turned off per session (account setting), and the same safety net covers them.
- **Accounting**: the owner's payment is the base amount, applied to the chosen charges; the surcharge is not an owner charge but card surcharge income in the journal export, Stripe's fee an expense, payouts move Stripe clearing to the bank. Payouts are copied daily (append-only) and offered for bank matching through `payments.sync.payouts_for_matching(start, end)`.
- **Three-way reconciliation** daily: ledger online payments against Stripe's balance lines and payouts (and, once wired, the bank deposits: hook `payments.sync.check_payouts_against_bank`). Any difference fails the "Online payments" health check, emails the board and sysadmins, and gives the treasurer a My item.
- Still needed before live payments: the HOA-owned Stripe account (EIN, bank account), Visa/Mastercard surcharge registration 30 days ahead, counsel-approved disclosure wording, and the go-live checklist in the runbook.

## D33-acctfix. Fixes from the accounting QA pass (2026-11-26)

An independent QA pass (`ledger/tests/test_accounting_scenarios.py`, `payments/tests/test_payment_scenarios.py`) found six bugs; each is fixed in the product code, and the scenarios are ordinary tests again. Choices the board should know:

**D33-acctfix-1. Money belongs to the ownership account it was posted under.** The ledger was per lot, so after a sale a seller's unapplied credit paid the buyer's dues. Every ledger entry now carries its `community.Account` (one ownership period), set when it is posted from its posting date: the account whose period covers that date (the sale date belongs to the buyers), a reversal or recorded refund follows the entry it corrects, an entry dated before the lot's first account belongs to that first account, one dated between two owners to the next owner's, and a lot that never had an owner keeps its entries without an account. A payment or credit is applied only to charges of the same account (`ledger/allocation.py`, `ledger/accounts.py`). After a sale the seller's credit stays as credit on the old, dormant account (the lot page shows "Credit owed to former owner"; the former owner sees it read-only on My history as "Credit owed to you", with any later entry on that dormant account, such as the board's refund), and a seller's unpaid charges stay theirs ("Still owed by former owner"); the buyers start clean. This replaces the earlier "balance brought forward" from the previous owner. Lot-level views add up the accounts (lot balance = sum of its accounts; open charges - unapplied credit == balance per account and per lot, checked by the QA invariants). Owner pages, the owner's statement, online payment amounts, the resale certificate, delinquency letters and courtesy reminders use the current owners' account; the board's lot page and the delinquency list show the whole lot. When a lot has had more than one owner, the board's payment, charge and credit forms offer the account (for example a refund check for a former owner's credit, posted as a charge on the old account, or a seller's arrears paid at settlement). Migration `ledger.0015_entry_accounts` assigns existing entries by date (only the new column is written, with the append-only trigger lifted for that backfill) and undoes any money already applied across two accounts with new append-only application rows. For the board and counsel: an unpaid assessment is a lien on the unit (68 Pa.C.S. § 5315), but the portal never moves a seller's debt to the buyer by itself; collecting it from the buyer would be a board decision recorded as a new charge.

**D33-acctfix-2. A late fee needs that month's dues still open.** `late_fee_candidates` tested the whole lot balance, so a lot that paid the month's dues on time but owed something else (even a charge not yet due) got a late fee. It now checks the open amount of the month's own assessment on the day the fees are posted, after the grace period of the late-fee rule; a prepayment that paid the dues means they are not late. The late list shows what is still open of that month's dues.

**D33-acctfix-3. Views as of a past date use only what had happened by then.** Each payment application now records `effective_on`, the posting date of the entry whose posting made it (the local date when credit is applied by hand). Aging and past-due amounts as of a date count only entries posted by then and applications in effect by then, so a check that bounced later still shows as paid on an earlier date. Migration `ledger.0012_application_effective_on` dates existing rows from the history: an undo row by the reversal that made it, any other row by the later of its two entries (an application made when a reversal freed money is dated by its own two entries, the closest the old rows allow).

**D33-acctfix-4. Every delinquency notice states the past-due amount.** Past due is the open amount of charges due before the day (open items, as of that day), not the balance netted against later charges or payments. The `{amount}` placeholder in every letter (the case letter sequence, the lot page's notices and the statement message) is that amount; the attached statement still shows the full balance under "Pay this amount".

**D33-acctfix-5. Refunds: the surcharge part in proportion, the payment part on the account.** A refund at Stripe of R from an online payment of T (base B + surcharge S) is split: the surcharge part is in proportion (card-network rules require a partial refund to return the surcharge pro rata), computed on the running total so the parts add up exactly: after refunds totalling R, round(R x S / T) of the surcharge has been refunded, all of it once R reaches T. The one exception is the debit-card safety net (D32-payments): a refund of exactly the surcharge owed back is all surcharge. The surcharge part is booked against surcharge income in the journal by itself (`payments.services.refund_portions`). The payment part reaches the books from the owner's account: either the board reverses the payment (a full refund; it also reopens the charges it paid), or presses "Record on the account" on the refund item, which posts a refund entry (`EntryKind.REFUND`, positive: the owner has the money back) booked against Stripe clearing. The portal still cannot refund (its key has no refund rights). A payment with a recorded refund cannot also be reversed, and the other way round, so a refund never counts twice. Surcharge-first was not chosen: it would return the whole surcharge on a small partial refund, which the card rules do not ask and which understates the surcharge income kept.

**D33-acctfix-6. Stripe payouts count in the bank reconciliation.** Online payments reach the bank only in Stripe payouts, never in deposit batches, so the cash book ignored them. A payout now counts as a deposit on its arrival date (`book_balance`, `uncleared`), is suggested for a bank-feed line of its exact amount within three days, and is ticked on the reconciliation page when Stripe reports it arrived or it is matched to a bank line; the board unticks one the statement does not show yet. Recorded as a cleared item of kind "payout" (migration `ledger.0013`, choices only). Online payments are never in deposit batches, so nothing is counted twice.

## D34-fixinfra. Fixes from the November regression: bank feed, outbound calls, host and backups (2026-11-26)

**D34-fixinfra-1. Account numbers are masked in bank-line descriptions, also in lines already stored.** Banks often put the other party's full account and routing numbers in a wire or ACH memo, and the portal must never hold bank account numbers (CLAUDE.md, D32-bankfeeds). Every bank-line description (Teller, OFX/QFX, CSV, the CSV preview, and again when lines are stored) now has each run of six or more digits (spaces or dashes allowed between them) replaced by "••••" and the last four digits (`ledger.bankfeeds.base.redact_numbers`). Kept as written: amounts (followed by cents, or after "$"), dates (6 or 8 digits that read as a date) and short numbers such as check numbers (five digits or fewer). When unsure it masks: losing part of a reference is better than keeping a number. Bank lines are append-only, but a stored account number would otherwise stay forever, in backups too. Removing data the app must never hold outranks the immutability of a free-text memo, so migration `ledger.0016_redact_bank_descriptions` masks existing descriptions in place: one UPDATE, run by the owner role that applies migrations, with the append-only row trigger lifted for that statement only (the pattern of governance 0005 and ledger 0012). Only `description` changes, and only on rows where masking changes it; amounts, dates and bank ids stay. One consequence: a CSV file (or an OFX file without FITIDs) imported before this fix whose lines carried such numbers would import those lines once more if the same file were imported again, because the line's id is computed from the masked text; ids are never computed from the unmasked number, since a hash of a description whose last four digits are shown could be reversed. Lines with a bank id (Teller, OFX with FITID) are not affected. *Update (fixres, BUG-004 / SEC-003 / R2-004):* the first masking let some numbers through (groups separated by dots, slashes or commas such as `1234.5678.9012` or `WIRE,000123456789,01`; 8-digit account numbers that happen to read as a date; a long run followed by `.00`; and a number cut at the 200-character cap, because the text was cut before masking). Now digit groups joined by a single space, dash, dot, slash or comma are one run; any run of eight or more digits written without separators is masked even if it reads as a date; a date is kept only when written with separators and real (2026-11-15, 11/15/2026), and it never joins a number next to it; cents are kept without a "$" only on small amounts (at most five digits of dollars); amounts after "$" stay. Masking runs on the full text and only then is it cut. Over-masking (an amount such as 1,234,567.89 without "$" becomes "••••6789") is accepted. Migration `ledger.0020_redact_bank_descriptions_again` applies the same masking (a frozen copy; 0016 is unchanged and its own frozen copy is still tested) to stored descriptions, with the row trigger lifted for that one UPDATE; a stored description of 190 characters or more that ends in digits has that last run masked whole, since the old order may have cut a number there.

**D34-fixinfra-2. Teller's Connect script stays unpinned: accepted residual risk.** The regression (SEC-005, R2-008) asked for the script to be pinned with a version and a Subresource Integrity hash. Teller documents only the unversioned `https://cdn.teller.io/connect/connect.js` and publishes no hash (checked 2026-11-26: Teller's Connect guide at teller.io/docs/guides/connect and a web search found no versioned path, npm package or hash; teller.io itself could not be fetched from the build environment). A hash computed from today's file would break the page whenever Teller updates it, and we do not invent one. So the one-page exception stays, narrowed: the CSP admits scripts from `https://cdn.teller.io/connect/` only (not the whole CDN host), the script tag sends no referrer, and the page still needs a fresh password or passkey check and is board-only. The remaining risk (a compromised Teller CDN could act as the board member on that page) is accepted as vendor trust, like Teller's handling of the bank sign-in itself; the runbook says how to limit it and to pin the script if Teller ever publishes a versioned URL or hash. Not done now: moving Connect into a separate origin or sandboxed popup with no session, which needs a second hostname and more set-up than the POC justifies; worth revisiting before production. *What the path restriction does and does not do (fixres, SEC-004):* `script-src https://cdn.teller.io/connect/` stops the page from loading a script from any other path of the CDN by a direct reference, for example a different script someone placed elsewhere on `cdn.teller.io`. It does not protect against a compromised or redirecting `/connect/` path: browsers check only the host after a redirect (CSP Level 3), so a redirect from `/connect/connect.js` to any other path on `cdn.teller.io` is allowed, and the script is unpinned, so whatever Teller serves there runs. `frame-src` and `connect-src` allow exactly `https://cdn.teller.io` and `https://api.teller.io` (whole hosts, no wildcard, no other Teller host); they were not narrowed to paths because the paths Connect's frame and requests use are not published and could not be checked from the build environment (teller.io and cdn.teller.io were unreachable), and a wrong path would break the bank sign-in, while a path would add little for the redirect reason above. A test keeps the three lists exactly as stated.

**D34-fixinfra-3. Host alerts must reach someone before a change is accepted; Falco's key is pinned.** The nightly integrity check accepts the new AIDE baseline, and the audit checkpoint and Falco offset move on, only after `host_alert` delivered the report to at least one sysadmin; `host_alert` now exits with an error when it reached nobody (no sysadmin email, or every send failed), and the timer then shows as failed on System status and sends the same report again next run (R2-006). Falco's apt key is trusted only with the fingerprint Falco publishes on its packages page (`478B2FBBC75F4237B731DA4365106822B35B1B1F`, checked 2026-11-26), and only that key goes into the keyring; a rotation needs a person to confirm the new fingerprint (`HOA_FALCO_KEY_FPR`) (R2-009). The off-site restore drill refuses a backup whose signed stamp is not the one in its name or lies in the future (R2-002). *Update (fixres):* the drill now picks the newest backup name that is well-formed and not dated in the future, warning about the ones it skips, so one mislabelled set in the bucket no longer blocks every drill (R2-005); the chosen backup's signed stamp must still match its name. A re-run of `harden-host.sh` keeps an installed Falco keyring when gpg shows it holds exactly the pinned key (one primary key with that fingerprint), so the step no longer needs falco.org; a first install, or a keyring holding anything else, still downloads and checks the key as before (R2-006). Not done: giving the app containers a write-only off-site token, which needs a change to the R2 token set-up.

## D34-fixmoney. Money belongs to the ownership period it is for (2026-11-26)

Fixes for the regression findings on ownership accounts and online payments (BUG-001 to BUG-010, SEC-001, R2-001, R2-004). Choices the board should know:

**D34-fixmoney-1. A sale recorded with an earlier date moves the buyer's entries to the buyer's account, by new records.** An entry's account is set when it is posted, from the account periods as they stand then. When the board records a transfer (or an ownership start or end) dated in the past, entries already posted for the buyer's time stayed on the seller's account: the buyer's dues and checks showed in the seller's history, and both balances were wrong. Now every change to a lot's account periods (`community.services.record_ownership`, `end_ownership`, `transfer_lot`, through `ledger.services.account_periods_change`) is followed in the same transaction by `ledger.services.move_entries`: each entry the old periods had put on an account by the rule, that now belongs to another account, is reversed on its old account and posted again, unchanged (same date, kind, amount, reference, month), on the right one; the copy points at the original (`LedgerEntry.moved_from`, migration `ledger.0016_entry_moves`, a new nullable column, no row updated). Rule 5 holds: nothing is edited, amounts never change, the runtime role keeps no UPDATE right, and one audit event (`ledger.entries_moved`) records the lot, the count and the accounts. A payment that had been applied to charges that moved too is applied to their copies; the deposit status follows the check (a moved check is not a new deposit, and its move is not a returned item). Owner pages, letters and the former owner's My history leave out a moved entry and its reversal (they cancel out and were never that owner's); the board's lot page shows both. Left where they are: entries whose account the board chose by hand (their account is not the one the old periods gave their date, e.g. a refund check for a former owner's credit), online payments (they belong to the payer, below), reversals and recorded refunds (they follow their entry), and an entry already reversed (the pair stays together). A late fee moves with the month's dues it penalises. The month's dues copy does not count against "one assessment per lot per month" (the reversed original still holds the month), so posting the month again adds nothing. If the board finds a moved entry really was the seller's (for example arrears paid at settlement recorded before the sale), it reverses the copy and records it again on the seller's account with the account choice on the form. Alternatives not chosen: changing the stored account in place (an UPDATE on an append-only table, which would need a weaker database grant), and refusing backdated transfers (the deed date is a fact the board must be able to record). *Update (fixres):* (1) The two-step path also moves (BUG-001): ending the seller's ownership with an earlier date moves nothing by itself (no account covers those dates, and nothing ever moves to "no account"), and the later step that records the buyer (Add owner or Transfer) moves the buyer-period entries. An entry counts as placed by the rule when its account is the one the old periods gave its date, or when the old periods gave its date no account, it is on the account whose period ended last before that date, and it was posted before that closing was recorded (new `community.Account.closed_recorded_at`, migration `community.0019_account_closed_recorded_at`); an entry the board posted on the closed account after the closing is its choice and stays. Accounts closed before this change have no recorded time and their entries count as the rule's. (2) The lot row is locked before the periods are read (BUG-007). (3) A moved payment keeps its charges (BUG-002): what it pays is read before anything is reversed, all copies are posted, and each payment copy is applied first to the copies of the charges its original paid, then the rest by the rule (`ledger.allocation.post_moved`). (4) The board is told (BUG-003, R2-003): each move creates an `EntryMoveNotice` (migration `ledger.0019_entry_move_notices`), a My items entry "Lot N: K entries moved to another account" with the accounts, linking to the list on the lot's account page, where the board marks it checked (audited `ledger.moves_checked`). Moved copies read "Moved from account N on <date>" on the board's lot page and on the owner's statement line (My account and the statement PDF), so a seller's settlement check that moved is easy to spot and put back with the account choice. Payments are still moved by date, not held back: a check dated in the buyer's time is normally the buyer's, and the board now sees every exception.

**D34-fixmoney-2. Late fees go with their dues; online payments with the payer.** A late fee is posted on the account of the month's dues it penalises (a seller's unpaid October dues give the seller's dormant account the fee, not the buyer). An online payment is posted on the account stored on its checkout when the payer started it, and applied to that account's chosen charges, even if the home was sold before Stripe confirmed it (a bank payment can take days); it is dated when Stripe says it succeeded (the balance line, else the charge), never before the checkout started or after today, not the day the poller saw it. If that account is no longer the current one, the board gets a "Payment from a former owner" item (refund any credit left). Receipts are shown only to the people of the account the payment is on. Checkout metadata never carries an empty value (Stripe drops those), and the check compares only what was sent.

**D34-fixmoney-3. The poller never loses a payment.** A returned bank payment is marked seen only in the same transaction as its reversal and board item, so a failure is retried; if part of the payment is recorded as refunded, the portal does not guess whether that refund went out before the return: the board gets an item to reverse the refund entry (if the refund did not go out) and then the payment. One payment's error never stops the poll of the others. An open checkout is marked expired only from Stripe's answer (session expired, or past its time and not paid); while Stripe cannot be asked it stays open and is asked again, and after three more days unanswered the board gets an item. *Update (fixres, BUG-005):* once its time is up, an open checkout is asked about hourly for a day, then daily, instead of every 15 minutes forever. When Stripe answers that it has no such session (for example after the test key is replaced or the Stripe account changes) at the three-day board item, the checkout is marked "Not found at Stripe" (`unreachable`, migration `payments.0003_checkout_unreachable`), audited (`payments.unreachable`), and no longer polled; the item tells the board to look in the Stripe dashboard. A checkout Stripe merely did not answer about (network) stays open and is asked daily.

**D34-fixmoney-4. Past-date views and the dashboard agree with the open items.** Migration `ledger.0017_redate_reversal_reapplications` corrects the dates migration 0012 gave to money re-applied in the step of a reversal (dated by its two entries, so a view as of a date before the reversal counted the payment twice): for each such row it appends a row undoing it from its old date and one applying it again from the reversal's date (0012 is not changed; totals never change). The dashboard's balance to-do takes "due since" from My account's figure (the oldest open charge of the current account), and the "Pay $X" button shows exactly what the payment page quotes for every charge the payer can choose (one function, `payments.checkout.quote_all`); when it quotes nothing, the button opens the page to type an amount. A former owner with two periods on the same lot sees each period with its own account.

## D45. Server errors are recorded by kind and described in plain words (2026-11-26)

3. **Who may set it up**: owners on the deed and authorized contacts (`payments.pay`), never view-only contacts, tenants, former owners, the manager or the homeowner preview, after a fresh password or passkey check (like connecting a bank feed). One enrolment per ownership account, shared by its payers: any payer sees it, replaces the method or turns it off. If the person who set it up can no longer pay for the home (left the account, login locked), it is cancelled at the next charge (`payer_left`).
4. **Stripe hosted pages only**: a Checkout Session in `mode=setup` for the account's Stripe Customer collects the card or bank account and, for a bank account, the ACH debit authorization (mandate) on Stripe's page. One Customer per ownership account and mode, created on first use with only internal ids as metadata (`account_id`, `lot_id`); no name or email is sent: Stripe's hosted page asks the payer for the email address it needs for the bank authorization and its receipts, and that stays at Stripe.
5. **Pull, never push**, bound like Pay online: the return is only a hint; an `AutopaySetup` row (random nonce, lot, account, person, login, method type, customer, 24-hour expiry) is created before the redirect, and the server accepts what it reads from Stripe only when the session (id, client reference, metadata, `mode=setup`, livemode, customer), the SetupIntent (id, metadata nonce, customer, livemode, succeeded) and the PaymentMethod (type, customer, mandate for a bank account) all match; anything else saves nothing and is audited (`payments.autopay_setup_mismatch`). A bank account waiting for micro-deposits is checked again by the 15-minute poller.
6. **What is stored**: Stripe ids (customer, payment method, mandate) and the display details Stripe returns (card brand and funding type, bank name, last four digits), on append-only `AutopayEvent` rows (enrolled, replaced, cancelled, failed, paused) with who and when; the state (on, paused, off) is derived from them. The last four digits and brand are display metadata Stripe itself shows, not a card or account number, so CLAUDE.md's rule holds; they appear only to the account's payers, never in the audit log or on the board's list.
7. **Charging**: each charge is a `PendingCheckout` (method bank, credit or debit from the saved card's funding) plus an append-only `AutopayAttempt` unique per account, month and try, sent as an off-session PaymentIntent (`confirm=true`, the mandate for a bank account) with the idempotency key `autopay-<account>-<month>-<try>`, so re-runs never charge twice. If Stripe does not answer, the next run first lists the Customer's PaymentIntents for one carrying this checkout's nonce, and only then sends again (same key while Stripe keeps it). The payment is recorded only when Stripe says succeeded, by the same verification and recording as Pay online (applied to that assessment charge through open-item allocation, on the payer's account, receipt emailed); a bank debit stays processing and is asked about every six hours until it settles. The surcharge is computed exactly as Pay online (credit cards only, rule `payments.credit_card_surcharge_bp`); a debit or prepaid card pays no fee, and the existing safety net asks the board to refund a surcharge if a card turns out not to be credit.
8. **Ceiling**: an amount above `payments.autopay_ceiling_percent` of the monthly dues (default 300%) is not charged; the board gets an "Automatic payment held back" item and an audit event. It can only trigger if the assessment amount itself goes wrong, since only the month's assessment is charged.
9. **Failures**: a decline, a payment needing the cardholder's authentication, or a failed bank debit is recorded (append-only, Stripe's decline code), emailed to the home's owners and the person who set it up (with the amount: it is their own account), and shown as a My items to-do "Your automatic payment didn't go through" with Pay now. Soft declines (insufficient funds, generic decline, try again later...) are retried once, three days later. A hard decline (expired, lost or stolen card, closed bank account, authentication required) or a returned bank payment pauses automatic payments at once rather than after a second failure, because charging a revoked or invalid method again only fails again and NACHA forbids re-presenting most returns; a second failure of a soft decline pauses too. Paused lasts until a payer sets up a payment method again.
10. **Ending**: turning it off is one button on My account, any time, audited, and detaches the payment method at Stripe. A sale or ended ownership (any change of a lot's account periods) cancels it for every closed account in the same transaction (`ownership_ended`) and detaches the method: accounts are per ownership period, so a buyer never inherits it. Replacing the method detaches the old one.
11. **Restricted key rights added** (runbook "Online payments (Stripe)"): Customers Write, SetupIntents Read, PaymentIntents Write, PaymentMethods Write (detach). Still no refund rights: the portal still cannot send money out.
12. **The board** sees, on Finance -> Online payments (board, `payments.manage`), every account's status, kind of method (card or bank), since when and its failures in 90 days, and the recent failures with their codes; no card or bank details.
13. `payments.autopay.describe_for_statement(account)` gives the monthly statement email one sentence ("This will be paid automatically on <date> from your Visa ending 4242 (card surcharge $6.00 included).", the bank variant, a retry or paused notice, a credit-covers notice) or None when not set up.

## D47. Automatic payments once a year, and board review above $500 (2026-11-26)

The owner asked for an annual choice ("some people might want to pay annually") and for "the limit on payments" to be "$500 before review". Built on D46, in test mode like it.

1. **Schedule.** Autopay has a schedule: Monthly (D46, unchanged) or Once a year with a month (a select, default January). It is chosen on the set-up page (stored on `AutopaySetup` and the enrol/replace `AutopayEvent`) and changed later on the Autopay page (`change_schedule`: payers only, fresh password check, an "I authorize" tick, an append-only `AutopayEvent` of kind `schedule`, audited `payments.autopay_schedule_changed`). A change takes effect from the next charge: what was charged stands, a yearly payment waiting for review under the old schedule is closed (outcome `closed`; a month's charge waiting for review stays), and a yearly payment chosen after this year's due day in that month starts the next year.
2. **What the annual charge is.** On the due day (`dues.due_day`) of the chosen month (with D46's week of catch-up), the next 12 monthly assessments starting that month: each month's assessment at its open amount if already posted (0 when paid), otherwise the monthly rule amount, less unapplied credit on the account. The card surcharge (credit cards only, `payments.credit_card_surcharge_bp`) applies to the whole amount.
   - **No uncovered months (bridge months).** Months are charged monthly under either schedule unless a yearly payment holds them. So before the first yearly payment, and between the end of earlier prepaid months and the next yearly payment, each month's assessment is paid automatically as a monthly charge (the same path, idempotency and review rule; credit first, so a month the credit covers costs nothing). The page says "Until your first yearly payment in <Month YYYY>, each month is paid automatically as usual."
   - **Changing the month.** Each yearly charge records the months it pays for (`covers_from`, the month it is charged, to `covers_through`). The next yearly charge pays for the 12 months starting with the later of its own month and the month after the prepaid months end, and its amount counts every month from its own month to that end, less credit (so the overlap is paid by the earlier credit). A later month leaves a gap that is bridged monthly; an earlier month buys the 12 months after the coverage ends. The page says which.
   - **No month charged twice, across schedules.** A month an annual attempt holds (made, in flight, or failed with the current payment method, while a retry is pending or payments are paused) is never charged monthly; for an annual payer neither is a month a yearly review holds (waiting, approved, declined or expired: a declined yearly payment is not replaced by monthly charges). A month a monthly attempt holds (made or in flight) counts nothing in a yearly amount.
3. **Drawdown reuses open-item allocation.** The payment is recorded by the same path as every Stripe payment (`checkout._record` -> `record_online_payment`), directed to the twelve months' already-posted open assessments; the rest is unapplied credit, which `LotBook.settle` applies to each month's assessment as it posts, exactly as a D30 prepayment. No new allocation path. Consequences people should know (said on the page): if the assessment amount changes mid-year the credit runs out earlier or later; and credit follows the association's normal order, so an *other* charge open on the account (a late fee) is paid from it first and the credit runs out sooner. After a sale the unused credit stays with the seller's account (D33); the buyer's account starts with nothing, and autopay is cancelled for the closed account as before.
4. **Idempotency.** One annual charge per account and year: `AutopayAttempt` period `"YYYY"` (with `schedule=annual`, `covers_from`/`covers_through` "YYYY-MM"), unique per account, period and try, Stripe idempotency key `autopay-<account>-annual-<year>-<try>`. Changing the month after this year's charge does not charge again this year. Monthly keys are unchanged.
5. **Authorization wording.** The set-up page shows, for each schedule, "about $X each month on the Nth" / "about $X once a year in <month> ... for the next 12 months' assessments", with the surcharge note for cards. Stripe's page carries the same sentence for the chosen schedule and month in the Checkout Session's `custom_text.submit.message` and the SetupIntent description; the ACH mandate itself is Stripe's standard reusable debit authorization, so our sentence is what names the schedule and amount. Check in test mode before live use that Stripe shows the message in setup mode.
6. **Review limit replaces the ceiling.** Rule `payments.autopay_review_cents` (money, default $500.00, citation "Board resolution adopting automatic payments", PA guidance: not covered by the Act; NACHA and card rules expect recurring charges within the authorization). `payments.autopay_ceiling_percent` is retired: it is removed from the registry and listed in `community.rules.RETIRED`; a value already recorded stays in the rule history and is ignored. Any automatic charge, monthly or annual, whose total including the surcharge is above the limit is not sent to Stripe: an append-only `AutopayReview` (one per account and period) records it, audited `payments.autopay_review_requested`. At $200 a month every annual payment needs approval, by design.
7. **Who decides.** A board member (`payments.manage`; never the manager) on My items ("Approve automatic payment of $X for <address>") or Finance -> Online payments ("Waiting for review"). Nobody decides a payment for a home they pay for or watch (owner on the deed, account contact, or the person who set it up), board member or not: the item is hidden from them and the service refuses. Decisions are append-only `AutopayReviewDecision` rows (one per review) and audited with ids and amounts only (the reason is in the row and the email, not the audit metadata).
8. **Outcomes.** Approved: charged on the next hourly run (`charge_approved`, even after D46's one-week window), through the same `AutopayAttempt` and key, so once; if the amount has grown above what was approved (the assessment changed), it is not charged and the board gets an "Automatic payment held back" item. Declined (a reason is required): nothing charged; the owners and the person who set it up are emailed with the reason and a link to My account; for annual, the months it would have paid are not charged monthly either (the payer pays by hand or switches to monthly). Not decided within 14 days: expired, nothing charged, the payers emailed. ## D52. Disbursements: surplus distributions and owner refunds, by statement credit or check (2026-11-26)

The owner asked for a way to pay money back to owners: when the reserves have met their target, and when a home is sold with a credit on the seller's account, by statement credit or by check. Built as Finance -> Disbursements (optional feature "disbursements", on by default; code in `ledger/disbursements.py`, pages in `ledger/disbursement_views.py`). Choices the board should know:

1. **Two kinds.** A *surplus distribution* splits a total the board enters across every home with an owner today; an *owner refund* pays back one ownership account's credit (usually a seller's dormant account, D33-acctfix-1). A third kind ("other") was not built: a one-off credit is already the lot account's Post credit, and a payment out of the association's money to one owner for any other reason should be an invoice.
2. **The split is a governing rule with a citation** (`disbursement.surplus_equal_shares`, default on): equal per home, matching the equal monthly assessment, because the portal records no per-home share of the common expenses. The cents that do not divide evenly go one each to the first homes in address order (largest-remainder method, `split_largest_remainder`; the same total always gives the same split). With the rule off the portal refuses to split and says why. **For counsel:** 68 Pa.C.S. § 5313 ("Surplus funds") says that, unless the declaration provides otherwise, surplus is paid to owners in proportion to their common expense liability or credited to them to reduce future assessments. Counsel should confirm what the Declaration says and whether reserve funds count as surplus at all (many declarations keep reserves for their purpose); the PA guidance (`community/pa_law.py`) and the proposal page say so. A surplus distribution cannot be proposed without the board resolution that decided it (one recorded in the portal, or its reference).
3. **Where the prompt comes from.** When the reserve balance (the Reserve plan's typed balance) is above the latest adopted plan's fully funded balance, Disbursements shows "Reserves are $X above target" and My items offers "Consider a surplus distribution" until a surplus distribution is proposed after the balance date. With no adopted plan there is no prompt, but a distribution can be proposed by hand.
4. **Approvals (append-only `DisbursementDecision`), like invoices.** A board member or the manager proposes; a different board member approves (never the proposer, never the manager); two approvers at or over `disbursement.second_approval_cents` (default $500, a rule with a citation), fixed when proposed. An owner on the refunded account may not approve a refund. A surplus distribution pays every owner, and board members are homeowners first (D20), so excluding recipients would leave nobody: a board member who receives part of it may approve, the approval is recorded as a recipient's, and the batch then needs two approvals besides the proposer. Declining needs a reason and ends the batch; a corrected one is proposed again.
5. **When money moves.** Proposing posts nothing. The final approval posts each statement credit (a `credit` entry, "Surplus distribution credit – 2026", applied by the open-item rule to open and future charges). Statement credits go only to open accounts: if a home is sold between proposal and approval the approval is refused. A check posts nothing until it is recorded as issued: a refund check then posts a `refund` entry of its amount on the account ("Refund by check #1042", reference "Refund check 1042"), which takes up the credit; a surplus check changes no owner account (the owner owes what they owed) and is booked from the fund to the bank. The refund amount is checked against the account's credit when proposed (less refunds already proposed), when approved and when issued.
6. **Checks without bank numbers.** The portal never knows the bank's account or routing numbers, so it does not print MICR checks. The treasurer either writes the checks in the bank's bill pay or the accounting package from the **check register** (CSV and PDF per batch: payee, mailing address, amount, memo, home and account), or prints them on the association's **pre-printed check stock** (the stock carries the bank's numbers and the check number): a PDF places the date, payee, amount in figures and words, memo and the payee's address for a window envelope at positions set under Check printing (hundredths of an inch, with an alignment test page). Then they record the check numbers ("Mark as issued", numbered in address order from the first number). A former owner's check goes to the forwarding address typed on the proposal, or their mailing address from their profile; never the home they sold.
7. **Clearing, voiding, stale checks.** "Mark cleared" records the date (suggested when the bank feed has an outgoing line of the same amount whose description carries the check number; the bank feed's own matcher offers the same match). The bank reconciliation lists issued, uncleared checks as outstanding payments and ticks the cleared ones. "Void" (board only, reason required) reverses the refund entry, so the owner's credit is open again and a new check can be written; a cleared or reconciled check cannot be voided. A check uncashed for 90 days becomes a My item with a note that Pennsylvania's unclaimed property law applies to long-uncashed checks: **the treasurer should confirm the dormancy period and the reporting steps with the PA Treasury** before voiding or reissuing (the portal cites no section for this).
8. **Accounting.** The journal export gets a "Disbursements" journal: a surplus statement credit is Dr the new setup account "Surplus distributions paid from" (`surplus_fund`, default "3100 Reserve and surplus fund") / Cr owner receivables; a refund check is Dr owner receivables / Cr bank; a surplus check is Dr surplus fund / Cr bank; voids and moved copies (a backdated sale moving a credit, D34-fixmoney-1) keep the same accounts with the sides swapped. The cash book subtracts issued checks and adds back voided ones.
9. **Owners** see a statement credit as a line on My account; checks to their current account under "Checks from the association" (amount, number, date, status; no address). A former owner sees "Refund of $X by check #N sent <date> to <address>" in My history. Nobody sees another account's amounts; every disbursement page is board, manager and auditor only.
10. **Records and audit.** Batches, lines, decisions, checks, check events and the entries they posted are append-only (model, trigger, runtime role). Every step is audited (`disbursement.proposed`, `approval_given`, `approved`, `declined`, `credit_posted`, `check_issued`, `check_cleared`, `check_voided`, `register_exported`, `checks_printed`, `print_settings_saved`) with ids, kinds, counts and amounts only, never names or addresses.

Serial numbers: one counter per Mailer ID (`ImbSerial`, taken under `select_for_update`), 9 digits after a 6-digit Mailer ID and 6 after a 9-digit one, never reused (a database constraint on Mailer ID and serial; the counter refuses to wrap), so each mailpiece is unique far beyond the 45 days the specification requires. Each letter's number, tracking code and ZIP routing are kept in an append-only `MailPiece` (mailing, letter group, home), allocated on the first print and reused on reprints so envelope and letter match. Routing is the ZIP or ZIP+4 from the last address line; no address-validation API is called (that would need USPS credentials), so delivery-point digits are not added. Reading scans is manual in Informed Visibility for now; importing IV scan data would need IV credentials through a server script and is a possible later step (done in D60).

## D56. Secret choices go through a mixing pool (2026-11-26)

An external review confirmed what D23 disclosed: a secret ballot's participation row ("this home voted") and its choice row were inserted in the same transaction, so PostgreSQL's system column `xmin` was identical on both and anyone with read access to both tables (the runtime role has it) could join them on (vote, `xmin`). Physical order, sequences and timestamps leak the same way. Elections (`ElectionParticipation` / `ElectionChoice`) and anonymous surveys (`SurveyParticipation` / `SurveyResponse` + `SurveyAnswer`) had the same layout. The owner directed a fix so that someone who reads the database after the fact cannot link a participation to a choice.

1. **Pool.** Casting writes the participation exactly as before (append-only, one per home or person, recusal and eligibility unchanged) and puts the choice in `governance.PendingSecretChoice`: the vote, election or survey, the option(s) or answers as JSON, a random UUID and a random sort key. No person, lot, ballot, participation id or timestamp. It is a staging area, not a record: not append-only; the runtime role may INSERT, SELECT and DELETE but not UPDATE or TRUNCATE it (`core.db_roles` insert/delete-only tables, applied by `apply_db_grants`). The permanent choice tables keep their append-only model, triggers and grants.
2. **Flush** (`governance/mixing.py`). Always in a transaction that writes no participation: a Procrastinate task (`governance.tasks.flush_secret_choices`, one queued per target) deferred after the cast commits, an hourly sweep (`sweep_secret_choices`), and the close paths (`close_vote`, `close_voting`, `close_survey`). It locks the vote/election/survey row (casting and closing lock it too), takes the pooled rows with `DELETE ... RETURNING`, shuffles them with `secrets.SystemRandom`, and bulk-inserts them into `SecretChoice`, `ElectionChoice` or `SurveyResponse`/`SurveyAnswer` in that order with fresh random UUIDs (random ids are stronger than sequence ids in shuffled order, and the tables already used them; no timestamp on any of them). Election picks and survey answers are shuffled again across ballots.
3. **Pool mix, not a plain threshold.** With K = `SECRET_BALLOT_MIX_MIN` (default 5, never below 2), an open target is flushed only when 2K choices wait, and a random K stay behind (re-inserted in the flush transaction, so they lose their link too). A plain "flush at K" would leave a final batch of one at close in the unlucky case, revealing that voter. With the pool mix every batch, including the last, holds at least K choices whenever K or more were cast; with fewer than K ballots in total the tally itself reveals about as much.
4. **Close and results.** Closing flushes everything inside the closing transaction before results exist (surveys flush just before the status changes, because the database refuses responses to a closed survey). `services.results`, `elections.tally`, `surveys.results` and the survey CSV export write anything still pooled first once nothing more can be cast (closed, or past the closing time or last day), so no final tally ever leaves a pooled choice out. While open, the board's live view counts only written choices and says how many more are "waiting to be mixed"; a formal vote's provisional outcome is withheld while any are pooled. Nothing per person is shown, logged or audited; the flush logs only the kind and a count.
5. **Residual risk.** While a choice waits in the pool (until 2K are waiting, or the close), its pool row and the participation share the casting transaction: someone with live database access in that window, a backup taken in it, or the write-ahead log can still link it. Deleted pool rows stay on disk until autovacuum reclaims them, and WAL segments until they are recycled. After the flush and VACUUM the persistent tables cannot be linked by transaction id, order, id, time or position; an observer can only tell which batch a choice was written in, and each batch mixes at least K ballots.
6. **Backups keep the pool.** `pg_dump --exclude-table-data` on the pool was considered and rejected: a restore made from a backup taken during an open vote would lose the pooled choices but keep the participations, and those homes could not vote again, so a binding vote would silently miss ballots. Vote integrity wins: backups include the pool (encrypted, two-person rules), so a backup taken during an open secret vote, election or anonymous survey holds up to about 2K pooled choices per open item whose dump order can be matched to the casting order. Once the item closes the pool is empty. `infra/poc/backup.sh` records the reason.
7. **Existing data.** Append-only choice rows written before this release are not rewritten or deleted; they keep the old, linkable layout. Only fictional demo votes exist, and they are counted together with the new rows. The board should not run real secret votes, elections or anonymous surveys on a release older than this one (0.25.0 on this branch).

This supersedes the "not unlinkable to a database administrator" limitation of D23 for choices that have left the pool.

(Points 1, 5 and 6 refined by D68, 2026-11-27: pooled choices are sealed before they reach the database, so the pool row the casting transaction writes, its WAL record and its place in a backup carry only ciphertext.)

## D58. Forgot password, fewer lockouts, and self-service account recovery with a waiting period (2026-11-26)

Owner decision. It relaxes "lost authenticators: two-board-member assisted reset, no self-service bypass" (D5) for ordinary accounts only.

1. **Forgot password (every account).** "Forgot your password?" on the sign-in page sends allauth's reset link (valid one hour, `PASSWORD_RESET_TIMEOUT_SECONDS`, single-use because the token changes with the password). Before the new-password form is shown, the person passes their passkey, authenticator app or a recovery code in that browser session (`accounts/password_reset.py`, which replaces allauth's view at the same URL). The reset never signs anyone in (`ACCOUNT_LOGIN_ON_PASSWORD_RESET = False`), so the next sign-in still asks for the second step. Afterwards every email address on file gets "Your password was changed". Audited: `password.reset_verified` (authenticator type), `password.reset_verify_failed`, `password.reset`. An account with no passkey or app is sent to the board.
2. **Fewer lockouts (every account).** My items (area "Sign-in and security") asks for a backup sign-in method until the login has two strong ones (two passkeys, or a passkey and the app), and for new recovery codes when two or fewer are left. Recovery codes are shown once: in the browser session that first opens a new set, which may also open a printable page and download them as a text file for 30 minutes (`accounts/recovery_codes.py`); elsewhere they are hidden and the person makes new ones. Each showing, print and download is audited (`mfa.recovery_codes_viewed`, `how` only); the codes are never logged. The sign-in help page explains recovery codes, another device or passkey, then recovery or the board.
3. **Self-service recovery (ordinary logins only).** Owners, authorized, view-only and tenant contacts, and former owners. Never anyone who holds, or held in the last 30 days, a board seat, an office or a manager, sysadmin, auditor or ARC reviewer role (or a Django staff flag): they use the assisted reset, which stays as it is for everyone. Flow (`accounts/recovery.py`): sign-in help, "I've lost my phone and recovery codes", an email address; the page always answers the same way and the view does the same work for every address (one lookup and one queued job carrying only a login id, 0 when unknown); the worker emails a single-use link valid one hour only to an eligible, active, enrolled login. Opening the link (swapped for a session marker) and confirming starts an `AccountRecovery` that waits `recovery.wait_hours`. At once every email address on file (sign-in, register and every extra email), the verified text number if the person opted in and the text feature is on, and the board (email through `send_now`, and a My items entry "Account recovery requested for <person> (<home>)" opening a page with Cancel) are told; every notice says "If this wasn't you, cancel" and links to a signed-in page where the person can cancel. Signing in with the existing passkey or app (or passing it on a password reset) cancels it automatically. After the wait the person asks for a new link, opens it, and in that browser session only finishes: every old passkey, app and recovery code is removed, every other session is signed out (`session_generation`), they are signed in there and the enrollment window of `accounts.enrollment` opens (via "recovery"), as after an invitation. New recovery codes come with the new authenticator. An unfinished request expires seven days after it became ready. Limits: one open request per login, at most three started per 30 days, five emailed links per login per day, and `ACCOUNT_RATE_LIMITS["account_recovery"]` (10 an hour per client, 3 per address). Audited with ids, states and counts only (`account_recovery.link_sent`, `.link_refused`, `.started`, `.cancelled`, `.completed`).
4. **Waiting period and lock are board settings.** `recovery.wait_hours` (default 48, at least 48, at most 336) and `recovery.lock_hours` (default 48, at least 24, at most 336) are governing rules in the "Sign-in and security" group of Community settings, with citations and PA guidance ("Not set by the Act; a board security policy"). Changes go through `set_rule` (audited). The values in effect when a request starts are stored on it, so a change applies to requests started afterwards. The floors are enforced both when a value is saved and when it is read. The Community setup wizard shows them on their own "Sign-in and security" step (after Privacy and retention). No new optional feature: recovery is always available to ordinary logins.
5. **Post-recovery lock.** For `lock_hours` after completion the account cannot cast a vote, an election ballot or a survey answer, give or revoke a proxy, add, remove or change email addresses or phones, change the mailing address, the official notice choice or text alerts, set up or cancel automatic payments, or ask for account changes. One helper, `accounts.recovery.refuse_if_locked(actor, what, error)`, is called by each of those services with its own error class, so views show "For your security, this is available again on <date time> because your sign-in was recently recovered." where they show any refusal. A banner says so on every page while it lasts. The board gets a My items entry "<person> recovered their sign-in; review if unexpected" for seven days.

Trade-off accepted by the owner: for ordinary accounts, someone who controls the person's mailbox can take over the sign-in if nobody reacts within the waiting period to the alerts sent to every channel on file. The wait, the alerts, automatic cancellation by a normal sign-in, the board's Cancel and the lock on votes, notices and payments limit what they could do. Staff accounts, whose power reaches other owners, keep the two-person reset only.

## D60. USPS tracking: importing Informed Visibility scans of paper mail (2026-11-26)

The owner decided (2026-11-26): build the import of USPS Informed Visibility (IV-MTR) scans for the barcoded paper mail of D55, with the statuses Mailed → Processed → "Sorted for delivery on <date>", a flag for the board when a letter has no scan after 5 days, the scan history kept as the record of mailing, the BCG login entered through a guided server script with a check command (USPS's test environment, CAT, first), and pull-only polling of pending pieces a few times a day within USPS's 30-day window, under USPS's 500 requests a minute.

**Switch and set-up.** Optional feature "usps_tracking" (Admin → Features), off by default. The association's Business Customer Gateway (BCG) login, a user given IV-MTR access by the account's Business Service Administrator (BSA) or a BSA Delegate, goes into the server's `.env` only, with `sudo bash infra/poc/set-usps.sh`: it asks the environment (cat by default, or production), the user name and the password at a hidden prompt, saves them with `set_env` (the password single-quoted so docker compose reads `$` and `#` literally; a password holding a single quote or a control character is refused), restarts the portal and runs `manage.py check_usps_iv`, which signs in only (no piece is looked up) and prints OK or what failed, never the login. The web app never takes or shows the password (CLAUDE.md, D36). Paper mail settings shows the set-up status ("Not set up: a sysadmin runs sudo bash infra/poc/set-usps.sh ...", "Connected to the USPS test environment (CAT). Last checked ...", "Connected to USPS Informed Visibility.", or the last failure).

**Client (`comms/usps_iv.py`).** Python's urllib, as `payments/stripe_api.py`: https only, default certificate verification, redirects refused, 15 second timeouts, and only the two configured hosts: CAT qiv.usps.com (API) and cat-services.usps.com (sign-in), production iv.usps.com and services.usps.com; `USPS_IV_API_HOST` / `USPS_IV_AUTH_HOST` may override them but only with *.usps.com names. Sign-in posts JSON to `/oauth/authenticate` (username, password, grant_type "authorization", response_type "token", scope "user.info.ereg,iv1.apis", USPS's published public client_id); the access token lasts 900 s and is renewed through `/oauth/token` with the refresh token, or by signing in again if USPS refuses the refresh. Tokens are kept in the worker process's memory only, never in the database, the cache table (which is in the database) or a log. A piece lookup is `GET /ivws_api/informedvisapi/api/mt/get/piece/imb/<31-digit IMb>` (tracking code + ZIP routing from the `MailPiece`), answering `{"data": ..., "message": ...}`: 200 with scans (scan time, operation code, facility city/state/ZIP, handling event type and mail phase are kept; the facility name, scanner and machine are not), 404 no scans yet, 403 not under our Mailer ID (recorded once as an append-only `MailPieceOutcome` and never asked again), 429 too many requests (wait as USPS says, once per run, then stop), 401 (sign in again once). Requests are paced evenly at 400 a minute. Only the status and a short code are logged, never bodies, tokens, the login or barcodes. Times without an offset are read in the portal's time zone.

**Polling (`comms/usps_tracking.py`).** A Procrastinate task every 4 hours (`41 */4 * * *`, maintenance queue) does nothing unless the feature is on and the login is set; otherwise it asks about each barcoded letter whose mailing is marked as mailed in the last 30 days and that is not final (sorted for delivery, delivered, or refused by USPS). New scans are stored append-only in `MailPieceScan`, once per (piece, scan time, operation code) by a constraint. A refused sign-in stops the run, fails the health check and emails the sysadmins at most once a day; `UspsPollState` (one row, no personal data) remembers the last attempt, success and failure. Audit `usps.polled` carries counts only (queried, new scans, not found, not ours, outcome).

**Statuses.** Mailed (marked as mailed, no scan), Processed (any scan), "Sorted for delivery on <date>" (operation codes 918/919, delivery point sequencing; 872 and 516 are read the same way should they appear), "Delivered on <date>" (517, should it appear), "No scans after 5 days" (mailed 5 or more days ago, never scanned), "Gave up after 30 days" (USPS keeps scans for 30 days), and "USPS would not show it" (403). Without an eDoc (electronic mailing statement, filed by bulk mailers) USPS gives only machine sortation scans, so "Sorted for delivery" is the last scan to expect; it usually means delivered that day or the next, and the pages say so.

**Where it shows.** The mailing page (board and manager) has a USPS tracking card: per letter the mailing address, status and last scan, and the counts ("5 sorted for delivery, 1 processed, 0 missing"). The meeting page's paper notice line reads "Paper notices mailed <date> to N homes — N sorted for delivery". My items lists "Paper notice to <address> has no USPS scan after 5 days — check the address" once per letter until a scan arrives, 30 days pass, or someone presses "Address checked" (append-only `MailPieceOutcome`, audited `mailpiece.checked` with the mailing id). System status has a "USPS tracking" check: not shown while off and not set up; OK "Not set up" when switched on without a login; failing when the sign-in is refused, every letter is refused, or no check succeeded for more than a day. With the feature off, the task asks nothing and the pages show none of it.

**Caveat.** USPS is modernizing its sign-in in 2026 and it is not confirmed whether the IV-MTR API's flow changes; test in CAT first (a CAT account comes from InformedVisibility@usps.gov) before production. Since 2026-09-12 a piece's scans are shown only to the owner of the Mailer ID / CRID on it.

## D61. Voting windows, automatic closing and live turnout (2026-11-26)

The owner asked: "Are the votes timeboxed and can the board see number of responses whilst a vote is underway?" Before this, a formal vote had an optional closing time (casting stopped after it, but the vote stayed open until the board pressed Close), elections had no window at all, and the board saw running per-option results while a vote was open. Now:

1. **Every formal vote and election is timeboxed.** Opening one needs an opening time (now or later) and a closing time, in the form and in the service (`governance/window.py` `check_window`). The closing time must be after the opening and at least the rule `vote.min_open_days` after the moment voting really opens (default 7 days, a board choice with a citation; no statutory fallback, because the Act sets no period for ballots outside a meeting: the Bylaws or counsel decide). A vote's window may be planned on the draft; an election's is set on Open voting. Before the opening time nobody can cast; ballot links say when voting opens and closes. Surveys keep their required first and last days.
2. **Closing by itself.** A Procrastinate periodic task (`governance.tasks.close_due_votes`, every 5 minutes) closes every vote, election and survey past its deadline through the normal close services as SYSTEM (`close_vote(..., at_deadline=True)`, `close_voting`, `close_survey`), which writes any pooled secret choices first (D56) and so makes the results final. The audit event carries `how: "deadline"` and no actor; the page says "Closed automatically at the deadline".
3. **No early close by default.** Owners rely on the deadline they were given, so the board closes a formal vote or an election before its deadline only when the rule `vote.allow_early_close` is on (default off), and then with a reason kept on the record (`how: "early"`). Old informal polls and votes without a deadline (demo data from before) can still be closed by the board. Trusted code (SYSTEM) may close.
4. **Extend once, never shorten.** Before the deadline passes, the board may move it later once, with a reason (`window.extend`, audited `vote.deadline_extended` with the hours added). Everyone who can vote is emailed at once (`comms.notify.send_now`), whatever their weekly digest choice: a deadline notice must not wait a week. A database trigger backs this up: once voting has opened, the opening time is fixed and the closing time can only move later.
5. **Reminder 48 hours before.** A periodic task (`vote_deadline_reminders`, every 15 minutes) emails, once per vote or election, the owners of homes that have not voted, each with a new personal single-use link (D24). Deadline-bound, so it goes at once with `comms.notify.send_now` whatever the person's digest choice, never into a weekly digest: the personal link travels only in that immediate email, and a link is created only for an email that is actually sent. Audited with the count.
6. **Live turnout, counts only.** On the vote, election and survey pages the board and the manager (`vote.turnout`; the manager never votes) see "N of M homes have voted (P%)" (formal votes and elections, per home; surveys and old polls per eligible person), the quorum needed and whether it is reached so far, and a progress bar. For formal votes and elections they also see **Who has voted**: the addresses of homes that have voted, with "by proxy" for elections, never a choice. Participation is not secret (it is part of the association's records); choices on a secret ballot are. The list can be downloaded as CSV (audited `vote.turnout_exported`).
7. **No running tallies for anyone.** While voting is open no one sees per-option counts, for any kind: formal votes (secret or not), elections and surveys (the survey results page and its CSV wait for the close). Results appear once voting has closed. This also keeps the D56 pool's "waiting to be mixed" count to the turnout card.
8. **Owners** see whether their own home has voted and the deadline; the overall turnout only when the rule `vote.show_turnout_to_owners` is on (default off). Never the list of who has voted.

## D68. Secret ballots: sealed pool, unlinkable by construction for everyone without the server's key (2026-11-27)

(Number to be assigned at merge; D67 may be taken by concurrent work.)

The owner asked for a review of the D56 pool: "the current implementation writes both records within the same database transaction, allowing someone with database access to correlate them through PostgreSQL transaction metadata such as `xmin` … backups and WAL may also preserve this relationship", and for "the smallest sound architectural change", without giving up one vote per eligible voter or ballot integrity, and with honest limits.

**What was wrong, exactly.** D56 put the choice in `PendingSecretChoice` as readable JSON, inserted in the casting transaction. Until a flush (2K waiting, or the close), that row and the participation (`Ballot`, `ElectionParticipation`, `SurveyParticipation`) carry the same top-level transaction id (for elections and surveys the participation sits in a savepoint, so its `xmin` is an adjacent subtransaction id, linked through `pg_subtrans` and the commit record). So during the voting window anyone who could run `SELECT xmin` with the runtime role, read a `pg_dump` (row order), a disk image, the WAL (each INSERT carries its xid and the full tuple, JSON included), dead tuples before VACUUM, or the slow-statement log (`log_min_duration_statement` prints parameters) could read *how each home voted*, not just that it voted. The dumps and off-site backups taken while a vote was open held that pairing indefinitely (D56 §6). The flush fixed only the permanent tables.

**Why not simply two transactions.** Writing the participation and the choice in separate transactions does not remove the link and breaks integrity. Consecutive xids, WAL order, LSN adjacency and commit times still pair them for a WAL or backup holder. A crash between the two either loses the ballot (participation first: the home "voted" and cannot vote again) or opens a double vote (choice first). Recovery would need a durable record tying the two, which is the link itself. Other options rejected for the same reason: staging choices in memory or a queue (lost on restart), holding casts for batch commits (the voter could not be told the ballot was recorded), excluding the pool from backups (rejected in D56: a restore loses ballots), random delays (do not change what the WAL records).

**Threat model.**
- *Other owners, the board, the manager, the auditor (through the portal):* see who voted (turnout, D61), never a choice. Unchanged.
- *A database reader without the server's environment* (runtime or owner role via SQL, a SQL injection, a read replica, `pg_dump` and the off-site backup bucket, someone holding the backup key, a restore drill, Postgres logs, WAL files or a pgdata copy without the `.env`): the main target of this change.
- *Root on the server, or a VM-level image* (Proxmox backup or snapshot) that holds both pgdata/WAL and the `.env`: holds the key. One trust domain on this deployment.
- *An active operator who changes the code or reads process memory:* can read every choice as it is cast, in any server-side design. Out of scope; mitigated only by two-person rules and audited updates.

**Decided.**
1. **Seal before the database.** The casting transaction stays as it is: participation and pooled choice commit together or not at all, under the target's row lock and the unique constraints, so a duplicate, a concurrent submission, a retry or a crash can never record a ballot without its choice or a choice without its ballot. But the pool row's only content column is now `sealed` (`governance/sealing.py`): AES-256-GCM, random 96-bit nonce and no timestamp (Fernet was rejected because its token carries the encryption time), key derived by HKDF-SHA256 from `DJANGO_SECRET_KEY`, associated data `kind:target_id` (a sealed row opens only for its own vote, election or survey). The plaintext is padded to one size per target (vote: fixed; election: by seats; survey: by its questions, with text at the worst-case JSON size), so length tells no choice from another. Oversize payloads are refused, never sealed shorter or longer. The readable `payload` column is gone (migrations 0018-0020; rows waiting at upgrade are sealed and re-inserted with new ids in the migration's own transaction).
2. **Only the flush opens, in memory.** `mixing.flush` takes rows with `DELETE … RETURNING sealed`, opens them in the worker, shuffles, and inserts the plaintext permanent rows (random UUIDs, no time) in one transaction that writes no participation. Choices kept behind (pool mix, K) are sealed again with fresh nonces, ids and sort keys, so a kept row cannot be followed from its casting row to the next batch. The plaintext choices therefore appear in the database and the WAL only in a flush transaction's inserts, mixed with at least K others, and nowhere tied to a sealed row. A pg_walinspect check in a scratch database confirmed this (`regression/manual.yaml`).
3. **Fail closed on the key.** If no configured key opens a pooled row, the flush raises `sealing.PoolKeyError`, the transaction rolls back, the row stays pooled, and the vote cannot close or show results on a partial count. Rotation: put the old key in `DJANGO_SECRET_KEY_FALLBACKS` (new setting, also used by Django for signatures) until every secret vote, election and anonymous survey open at the rotation has closed. A restore into an environment with another `DJANGO_SECRET_KEY` needs the original key for ballots pooled at backup time.
4. **Unchanged:** eligibility, recusal and proxies; one ballot per home or person (unique constraints, row lock); the D24 personal links and re-authentication; append-only permanent tables (model, trigger, runtime-role grants); the pool stays insert/delete-only for the runtime role; backups keep the pool (now ciphertext), so no ballot is lost on restore; results flush before counting; the audit records that a ballot was cast for a home, never a choice; flush jobs carry only the kind and target id; the flush logs only the kind and a count.

**What it guarantees.** For anyone without the server's key, no persisted relationship links a home to its choice: the transaction id, WAL position, dump order, TOAST chunks and slow-statement log pair each participation only with an opaque, equal-sized ciphertext; no permanent choice row shares a transaction id, id, time, sequence, order, job row or audit row with any participation; every batch mixes at least K choices (all of them if fewer than K were cast). Proof of participation stays: the participation row, the audit event and the voter's "you voted" page. Results stay complete and checkable: written plus pooled choices always equal the ballots cast, and nothing is counted until every pooled choice is written.

**Residual risks (disclosed to the board).**
- *Key and data together.* Root on the server, or a VM image holding both the `.env` and pgdata/WAL from the voting window (or old backups plus the key later), can open each sealed row and link it. Full unlinkability against that holder needs a second trust domain the owner has not decided on: a ballot key whose private half the server never holds (board members, threshold), homomorphic or mixnet tallying, or an outside teller. Each is a larger design with key ceremonies and recovery risks; for a 44-lot community the owner may accept the server operator as trusted, under the two-person rules.
- *An active operator* sees choices in the request; no server-side design prevents that.
- *Batch level.* An observer of the permanent tables over time can tell which batch a choice was written in; each batch holds at least K choices, and with fewer than K ballots in total the tally itself reveals about as much.
- *Free text* on anonymous surveys can identify its writer by content; padding hides its length only.
- *Older data.* Choices written before D56 keep their old layout; dead tuples and WAL from before this release may still hold readable pooled JSON until VACUUM and WAL recycling, and backups taken during open secret votes before this release still do: keep them under the two-person rules or expire them.
- *Timing.* Turnout times (D61) and batch times are visible to the board and the database; they say who voted and when, not how.
