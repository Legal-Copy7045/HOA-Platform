Restore from a backup

Puts the whole portal back to one backup point: its database and its files. The portal only asks; the server's own agent checks the backup point against the backups it really has and does the restore (decision D98).

What happens

  1. The board and the sysadmins are emailed that you asked, and again when it has finished.
  2. A safety backup of the portal as it is now is taken first. If it fails, nothing is changed. It is kept (not removed after 14 days) and, when off-site backups are set up, copied off-site.
  3. The portal stops. Its database is emptied and the chosen backup is loaded; the backup's files are put back into the file store.
  4. If the backup was made by an older release, it is brought up to the installed release{% if installed %} ({{ installed|join:"." }}){% endif %}. A backup made by a newer release is refused: install that release first.
  5. The portal starts again and is checked. If any step fails, the server puts the safety backup back the same way.
{% icon "alert" %}{{ confirm_text }}

Why the backup's logins, not today's: a login belongs to the people, roles and records around it. Keeping today's logins on top of older data would give back access that was removed after the backup and could point logins at the wrong person, and it would bring back nothing that was lost. So the backup is restored as it was, and every session is ended. If your own login was created after the backup, or your passkey was added after it, sign in with what you had then, or have another sysadmin from the backup sign in. A demo reseed is different: it keeps real logins because demo data has none.
